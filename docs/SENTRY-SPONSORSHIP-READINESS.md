## Why sponsored Sentry infrastructure fits the public toolkit

The toolkit is public developer infrastructure for an under-served web-engineering domain. It has executable browser and package workloads rather than only documentation. Relevant public evidence includes:

- browser verification in Chromium, Firefox, WebKit and mobile Chromium;
- Node 22, 24 and 26 quality lanes;
- machine-readable partner/interoperability workloads and evidence summaries;
- localization QA for key/placeholder integrity and RTL/bidi-sensitive failure modes;
- accessibility regression tests and direction-aware interaction primitives;
- CodeQL, Dependency Review, OpenSSF Scorecard and Security Insights evidence;
- a public npm release and release-integrity controls;
- CodeMeta and CITATION metadata plus reusable research/evidence assets.

A sponsored Sentry account would be used only for legitimate observability of public toolkit/demo/integration surfaces and related open-source engineering workflows. It would not be used as a justification to send private health data, protected editorial content, credentials, or unnecessary personally identifiable information to Sentry.

## Proposed application description

Rawafid Arabic/RTL Accessibility & Localization Toolkit is a public Apache-2.0 TypeScript project that provides framework-agnostic infrastructure for Arabic and bidirectional interfaces, localization QA, accessibility interactions, Unicode-safe text handling and browser interoperability. The project publishes executable cross-browser workloads, machine-readable QA/evidence contracts, security posture documentation and a public npm release. We are seeking sponsored Sentry access to strengthen observable, reproducible reliability of the public open-source toolkit and its controlled demo/integration surfaces without introducing financial risk to our self-funded public-interest initiative.

## Privacy and telemetry boundary

Before enabling Sentry on any Rawafid surface:

1. Define the exact public engineering surface being monitored.
2. Minimize event payloads and avoid health/content data not required for debugging.
3. Remove or scrub authentication tokens, emails, free-text health notes and other sensitive values from telemetry.
4. Keep environment and release tagging explicit so public toolkit evidence cannot be confused with production clinical/editorial workflows.
5. Set sampling/retention/configuration consciously rather than inheriting defaults without review.
6. Validate that source maps, logs, traces and replays do not expose protected data before enabling them.
7. Document the integration and its boundaries in the repository after, not before, the account is actually approved and configured.
