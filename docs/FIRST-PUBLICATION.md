# First npm publication checklist

This document covers the one-time bootstrap required before routine npm Trusted Publishing releases can begin.

## Why the first publication is different

The package is published under:

```text
@rawafid/arabic-rtl-a11y-toolkit
```

Routine releases are designed to use npm Trusted Publishing/OIDC from `.github/workflows/release.yml`, avoiding long-lived publication credentials. The first publication may use a tightly scoped granular npm access token from a GitHub secret so the package can be created and provenance can still be generated by GitHub Actions.

The token must never be committed to the repository, echoed in logs, copied into documentation, or exposed to pull-request workflows.

## 1. Namespace ownership

Before publishing, confirm that the maintainer controls the `rawafid` npm organization/scope and that the publishing identity has write permission for the intended package or scope. If ownership is uncertain, stop. Do not publish under a lookalike or unrelated namespace.

## 2. Bootstrap credential requirements

The one-time credential should be an npm granular access token with the minimum package/scope permissions necessary to publish. If npm's 2FA policy requires it for automated direct publishing, the token must be configured appropriately for that policy.

The credential is stored only as a GitHub Actions secret and is consumed only by the temporary bootstrap workflow. All non-publish verification steps run before the credentialed step.

## 3. Bootstrap release gate

The temporary bootstrap workflow is locked to the canonical repository, `main`, the exact package identity, and the exact bootstrap version. Before publication it must:

1. synchronize root `package-lock.json` release metadata with `package.json`;
2. run deterministic `npm ci`;
3. run the complete `npm run check` gate;
4. inspect the npm package contents;
5. build exactly one release tarball;
6. compute the local SHA-512 tarball integrity;
7. generate an SPDX SBOM;
8. retain bootstrap evidence as a GitHub Actions artifact.

The publish step must not execute if any earlier gate fails.

## 4. One-time automated publication

The bootstrap publishes the exact prebuilt tarball rather than rebuilding implicitly at the registry boundary:

```bash
npm publish <exact-tarball.tgz> --access public --provenance
```

Authentication is supplied through `NODE_AUTH_TOKEN` from the GitHub secret. GitHub Actions also has `id-token: write` so npm provenance can be generated from the supported CI environment.

After publication, the workflow queries npm for `dist.integrity` and requires it to equal the locally computed tarball integrity. A mismatch fails closed.

## 5. GitHub Release binding

Only after registry identity has been verified does the bootstrap create the matching GitHub Release/tag for the exact release commit. The normal `release.yml` workflow is then triggered by the published GitHub Release and performs its own release validation/evidence path. Because npm versions are immutable, that workflow detects the already-published registry version and verifies it rather than attempting to overwrite it.

## 6. Configure Trusted Publishing immediately after bootstrap

For GitHub Actions, configure the npm package to trust:

- repository owner/user: `khaledaltheeb`
- repository: `rawafid-arabic-rtl-a11y-toolkit`
- workflow filename: `release.yml`
- environment: `npm`
- allowed action: direct publish, or a stricter staged-publish policy if deliberately adopted later

The npm trusted-publisher mapping must point at the workflow filename exactly.

## 7. Remove the bootstrap credential path

After a successful bootstrap and trusted-publisher configuration:

- delete the temporary bootstrap workflow;
- remove/revoke the granular publication token when it is no longer needed;
- verify that no routine workflow references the bootstrap secret;
- retain account-level 2FA;
- protect the GitHub `npm` environment and release/tag paths;
- periodically audit the trusted-publisher mapping.

Routine new versions must use `.github/workflows/release.yml` and OIDC/Trusted Publishing rather than recreating a token-based path.

## 8. Verify the first routine OIDC release

On the next version, confirm:

- the release workflow publishes without a publication token;
- npm Trusted Publishing authentication succeeds;
- provenance is attached;
- package version, repository URL, exports, and registry integrity are correct;
- SBOM and retained release evidence are present;
- a clean consumer can install and import the package.

## Abort conditions

Do not publish if any of these is unresolved:

- npm scope ownership is uncertain;
- the token lacks the correct least-privilege package/scope permission;
- release version or repository identity differs from the locked bootstrap target;
- CI, package, security, or browser evidence is red;
- the package tarball contains excluded Rawafid material, credentials, `.env` material, or private data;
- account/publishing 2FA policy is not satisfied;
- repository/package metadata does not point to the canonical public repository;
- local tarball integrity cannot be verified against the registry after publication.
