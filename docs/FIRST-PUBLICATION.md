# First npm publication checklist

This document covers the one-time bootstrap required before routine OIDC-based releases can begin.

## Why the first publication is different

npm Trusted Publishing is attached to an existing registry package. A brand-new package must therefore be created first before the repository can establish its trusted-publisher relationship.

The bootstrap must remain a human-controlled registry operation. Do not solve this by committing or storing a long-lived publication token in the repository.

## 1. Namespace ownership

The package currently uses the name:

```text
@rawafid/arabic-rtl-a11y-toolkit
```

Before publishing, confirm that the maintainer controls the `rawafid` npm organization/scope and has write permission. If that scope is not controlled, stop and select a namespace that is actually owned; do not publish under a lookalike or unrelated scope.

## 2. Account security

- Enable npm account-level 2FA.
- Review recovery methods before publishing.
- Do not create a bypass-2FA automation token merely to perform the bootstrap.
- Use a trusted maintainer workstation and a clean checkout of the reviewed release commit.

## 3. Verify the release candidate

From the exact reviewed commit:

```bash
npm ci
npm run check
npx playwright install --with-deps chromium firefox webkit
npm run test:e2e
npm pack --dry-run
```

Verify:

- version matches the planned Git tag/release;
- package contents contain only the declared public OSS scope;
- no Rawafid scientific/editorial corpus is present;
- no credentials, `.env` secrets, local artifacts, or private data are present;
- exported JavaScript, types, CSS entry points, README, LICENSE, and NOTICE are present.

## 4. One-time bootstrap publish

Publish interactively with npm's normal authenticated 2FA path:

```bash
npm publish --access public
```

Do not run the GitHub OIDC release workflow until the package exists and its trusted publisher has been configured.

## 5. Configure Trusted Publishing immediately

For GitHub Actions, configure the existing package to trust:

- repository owner/user: `khaledaltheeb`
- repository: `rawafid-arabic-rtl-a11y-toolkit`
- workflow filename: `release.yml`
- environment: `npm` if the GitHub environment is used
- allowed action: `npm publish` (or a stricter staged-publish policy if deliberately adopted later)

The workflow itself is `.github/workflows/release.yml`; npm's form expects the workflow **filename**, not the full path.

## 6. Verify OIDC on the next release

The next release should be performed through the reviewed GitHub Release -> `release.yml` path. Confirm:

- OIDC authentication succeeds without `NPM_TOKEN`;
- npm provenance is attached;
- package version, integrity, repository URL, and exports are correct;
- SBOM artifact is generated by GitHub Actions;
- a clean consumer project can install and import the package.

## 7. Lock down publishing

After Trusted Publishing has been proven:

- remove/revoke any publication credential no longer required;
- choose npm's strongest appropriate publishing-access policy compatible with Trusted Publishing;
- keep account-level 2FA enabled;
- protect release tags and the GitHub `npm` environment;
- periodically audit the trusted-publisher mapping.

## Abort conditions

Do not publish if any of these is unresolved:

- npm scope ownership is uncertain;
- release commit/version does not match the planned release;
- CI or browser tests are red;
- package tarball contains excluded Rawafid material or secret-like content;
- account 2FA is not enabled;
- repository URL/package metadata points somewhere other than the canonical public repository.
